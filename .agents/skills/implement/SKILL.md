# implement

## 入力

- `specification`: 実装したい機能の仕様（目的、期待される動作、入力/出力の例など）
- `target_path`: 実装対象となるパッケージまたはファイルパス（不明な場合は仕様から判断・提案する）

## 手順

1. **仕様の理解と確定**
    - `specification` を読み込み、実装に必要な情報を整理する。
    - 実装場所 (`target_path`) を特定する。
    - 既存コードの構造、命名規則、依存関係、関連テストを確認する。
    - 既存の実装方針やプロジェクトの規約がある場合は、それらに従う。
    - 不明点や曖昧な点（仕様の境界条件など）があれば、ユーザーに質問して確定させる。
    - 実装方針とテスト方針を整理し、仕様との矛盾がないことを確認する。

2. **Gitブランチの作成**
    - 実装開始前に、Gitリポジトリ内であることを確認する。
    - `git status` を実行して現在の作業ツリーの状態を確認する。
    - 現在のブランチを確認する。
    - 以下の命名規則で機能開発用ブランチを作成する。

      ```bash
      git switch -c features/<implement内容>
      ```

    - `<implement内容>` は実装する機能の内容を英語の kebab-case で簡潔に表現する。
      - 例: `features/add-sql-logger`
      - 例: `features/add-file-rotation`
      - 例: `features/fix-log-level-filter`
    - ブランチ名は仕様と実装内容に対応したものにする。
    - 同名ブランチがすでに存在する場合は、既存ブランチを勝手に使用せず、別名を検討する。
    - 作業ツリーに未コミットの変更がある場合は、その内容を確認する。
      - ユーザーの変更を勝手に破棄、上書き、リセット、stash しない。
      - 既存の変更が今回の作業に影響する場合は、ユーザーに確認する。
      - 安全にブランチを作成できない場合は、作業を中断してユーザーに確認する。
    - ブランチ作成に失敗した場合は、原因を確認し、勝手に別の方法でGitの状態を変更しない。
    - ブランチ作成後、`git branch --show-current` で作成したブランチに切り替わっていることを確認する。

3. **テストの作成 (TDD)**
    - `target_path` に基づき、テストファイル (`*_test.go`) を作成または更新する。
    - 仕様を満たすテストケースを記述する。
    - 正常系、異常系、境界条件を考慮する。
    - 必要に応じて既存テストも更新する。
    - テスト作成後、`go test ./...` を実行する。
    - 新しく追加したテストが、期待どおりに失敗することを確認する。
    - 失敗理由が未実装の機能によるものであることを確認する。
    - コンパイルエラーやテストコードの誤りによる失敗を、TDDの意図した失敗として扱わない。
    - 既存テストが最初から失敗している場合は、その内容を確認し、今回の変更と無関係であればユーザーに報告する。

4. **実装**
    - テストをパスするように、最小限の実装を `target_path` に追加または修正する。
    - 既存の設計方針、命名規則、コーディング規約に従う。
    - 仕様にない機能を独断で追加しない。
    - 今回の実装に直接関係しない既存コードは変更しない。
    - 必要以上に抽象化や複雑化を行わない。
    - テストを通すためだけの不自然な実装を行わない。

5. **テストの検証**
    - `go test ./...` を再実行する。
    - すべてのテストがパスすることを確認する。
    - 失敗した場合は原因を調査し、実装またはテストを修正する。
    - 修正後は必ず再度テストを実行する。
    - 既存テストを含め、プロジェクト全体のテストが通ることを確認する。

6. **品質ガード**
    - 以下のコマンドを実行する。

      ```bash
      go fmt ./...
      golangci-lint run ./...
      ```

    - `go fmt` による変更が発生した場合は、変更内容を確認する。
    - `golangci-lint` で問題が検出された場合は、原因を調査して修正する。
    - 品質ガードの修正後は、手順5に戻ってテストを再実行する。
    - 品質ガードを通過するまで必要な修正と検証を繰り返す。
    - 環境や依存関係の問題で実行できない場合は、その事実を明確に報告し、成功したものとして扱わない。

7. **完了報告と振り返り**
    - 以下の内容を整理してユーザーに報告する。
      - 実装した機能の概要
      - 変更・追加したファイル
      - 作成したテストケースの概要
      - テスト実行結果
      - `go fmt` の実行結果
      - `golangci-lint` の実行結果
      - 作成したGitブランチ名
      - 未解決の問題や注意事項
    - `retro` スキルを呼び出して、業務の振り返りを行う。
    - `retro` の結果も必要に応じて完了報告に含める。

## 判断基準

- 仕様が明確になっているか？
- 実装対象 (`target_path`) が適切か？
- 機能開発用のGitブランチが作成されているか？
- テストが失敗しているか？（TDDのプロセスにおいて、意図した失敗であることを確認する）
- 実装がすべてのテストをパスしているか？
- `go fmt` が正常に実行されているか？
- `golangci-lint` がエラーを出していないか？
- 既存機能に意図しない変更や影響が発生していないか？

## 完了条件

- 仕様が確定している。
- 機能開発用のGitブランチが作成されている。
- TDDに従ってテストが作成されている。
- すべてのテストがパスしている。
- `go fmt` を実行済みである。
- `golangci-lint` を通過している。
- `retro` スキルが呼び出されている。
- 実装内容と検証結果がユーザーに報告されている。

## 禁止事項

- テストを書かずに実装を進めること。
- テストが失敗した原因を確認せずに実装を進めること。
- 品質ガード（`go fmt`, `golangci-lint`）を無視して完了すること。
- ユーザーの未コミット変更を勝手に破棄、上書き、リセット、stash すること。
- ユーザーの許可なく既存ブランチを削除すること。
- 今回の仕様に関係のないコードを不用意に変更すること。
- テストや品質ガードの失敗を隠して完了扱いにすること。
- `retro` を呼び出さずに終了すること。
- ユーザーの許可なく `git commit` や `git push` を実行すること。
