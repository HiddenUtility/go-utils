# improve-skill

## 1. 目的

`retro` のKPIレポート、`eval-skill` の評価レポート、および過去のレポートに記録された成功事例・失敗事例をもとに、既存スキルの品質を改善する。

改善対象は、正式版の次のファイルとする。

`.agents/skills/<skill-name>/SKILL.md`

改善が必要な場合は、正式版の `SKILL.md` を直接編集する。

編集後はGit commitを作成し、`eval-skill` を実行して改善結果を評価する。

再評価でさらに改善が必要と判断された場合は、同じ処理を繰り返す。

改善が不要になった場合は、`git-create-pr` スキルを使用する。

## 2. 起動トリガー

このスキルは、原則として他のスキルから呼び出されて実行する。

主な呼び出し元は次の2つとする。

| 呼び出し元 | 呼び出すタイミング |
|---|---|
| `retro` | KPIレポートを作成し、対象スキルの改善が必要と判断したとき |
| `eval-skill` | 評価レポートを作成し、対象スキルの改善が必要と判断したとき |

ユーザーが直接実行を依頼するケースも受け付ける。ただし、その場合も本書で定義する必須入力を満たす必要がある。

### 2.1 retroからの呼び出し

`retro` はKPIレポートを作成した後、対象スキルの改善が必要と判断した場合に `improve-skill` を呼び出す。

呼び出し時には、少なくとも次の情報を渡す。

- `skill-name`：改善対象のスキル名
- `retro-report`：作成したKPIレポートのパス

### 2.2 eval-skillからの呼び出し

`eval-skill` は評価レポートを作成した後、対象スキルの改善が必要と判断した場合に `improve-skill` を呼び出す。

呼び出し時には、少なくとも次の情報を渡す。

- `skill-name`：改善対象のスキル名
- `eval-report`：作成した評価レポートのパス

### 2.3 呼び出し時の共通ルール

- 呼び出し元は `retro` または `eval-skill` を基本とする。
- 呼び出し元は改善対象の `skill-name` を明示的に渡す。
- 呼び出し元は作成したレポートのパスを渡す。
- 呼び出し元から渡されたレポートは、必ず読み込む。
- 呼び出し元から渡されたレポートだけで改善判断を完結させてはならない。STEP 4で定義する関連レポートの確認を行う。
- 呼び出し元が改善不要と判断している場合は、原則として本スキルを呼び出さない。

### 2.4 skill-nameを特定できない場合

`skill-name` は必須入力である。

次のいずれかによって対象スキルを特定できること。

1. 呼び出し元から渡された `skill-name`
2. 呼び出し元から渡されたレポートの保存先パスに含まれるスキル名

呼び出し元から `skill-name` が渡されておらず、レポートの保存先からも特定できない場合は、改善処理を開始してはならない。

その場合は、次のように処理する。

1. `skill-name` を特定できないことを呼び出し元に伝える。
2. 呼び出し元に `skill-name` の確認を依頼する。
3. 対象が特定できるまで、ファイルの編集、Git commit、評価、PR作成を行わない。

複数のスキルが候補になる場合も、推測で対象を選択してはならない。

## 3. 入力とレポートの保存先

### 3.1 必須入力

| 項目 | 説明 |
|---|---|
| `skill-name` | 改善対象のスキル名 |
| レポート | `retro` のKPIレポート、または `eval-skill` の評価レポートのいずれか |

2種類のレポートを両方用意する必要はない。どちらか一方があれば処理を開始できる。

ただし、改善判断では原則として両方のレポートを確認する。片方しか存在しない場合は、存在するレポートを使って判断し、存在しないレポートについては未確認であることを明確にする。

### 3.2 eval-skill 評価レポート

保存先：

`docs/eval-reports/<skill-name>/<datetime>.md`

### 3.3 retro KPIレポート

保存先：

`docs/retro-reports/<skill-name>/<datetime>.md`

### 3.4 改善対象スキル

改善対象ファイル：

`.agents/skills/<skill-name>/SKILL.md`

`skill-name` と対象ファイルの対応が正しいことを確認する。

対象の `SKILL.md` が存在しない場合は、新しいスキルを作成せず、呼び出し元に問題を伝えて停止する。

## 4. レポートの調査と改善要否の判断

改善方針を決定する前に、必ず関連レポートを調査する。

**特定のレポートだけを読んで、すぐにSKILL.mdの修正を始めてはならない。**

特に、スキルの大幅な変更や作り直しを検討する場合は、過去の成功事例を確認することを必須とする。

### 4.1 現在のレポートを確認する

次の2種類のレポートを確認する。

#### eval-skill 評価レポート

保存先：

`docs/eval-reports/<skill-name>/`

確認する内容：

- 呼び出し元から渡された評価レポート
- 同じスキルに関する最新の評価レポート
- 必要に応じて、過去の評価レポート

#### retro KPIレポート

保存先：

`docs/retro-reports/<skill-name>/`

確認する内容：

- 呼び出し元から渡されたKPIレポート
- 同じスキルに関する最新のKPIレポート
- 必要に応じて、過去のKPIレポート

呼び出し元が `retro` の場合でも、`eval-skill` の評価レポートを確認する。

呼び出し元が `eval-skill` の場合でも、`retro` のKPIレポートを確認する。

**呼び出し元がどちらであるかに関係なく、両方のレポートを確認すること。**

片方の保存先にレポートが存在しない場合は、その事実を記録し、存在するレポートを使って判断する。

### 4.2 過去の成功事例を調査する

過去のレポートを調査し、対象スキルでうまく機能していた仕様、手順、設計、改善内容を把握する。

特に次の情報を探す。

- 過去にKPIを達成した事例
- 過去に評価でPASSとなった事例
- 過去に改善効果が確認された変更
- 安定して動作していた処理手順
- 再現性が確認できた仕様やルール
- 過去の失敗を解消した改善内容
- 維持すべき機能や振る舞い

過去の成功事例は、単なる参考情報ではなく、改善時に維持すべき重要な情報として扱う。

現在の問題を解決するために、過去の成功事例を不用意に削除・変更してはならない。

過去の成功事例と現在の改善方針が矛盾する場合は、その理由を明確にしてから変更する。

過去の成功事例が見つからない場合は、見つからなかったことを記録し、成功事例が存在すると仮定してはならない。

### 4.3 大幅な変更・作り直しを検討する場合

以下のような変更は、大幅な変更・作り直しとして扱う。

- スキルの目的や責務を変更する。
- スキルの処理フローを大きく変更する。
- 既存の手順を全面的に置き換える。
- 既存の仕様やルールを大幅に削除する。
- SKILL.mdをほぼ全面的に書き直す。

この場合は、次の確認を必須とする。

1. 過去のKPIレポートを調査し、成功した実行事例を確認する。
2. 過去の評価レポートを調査し、PASSとなった評価事例を確認する。
3. 成功事例で有効だった仕様・手順・設計を抽出する。
4. 今回の作り直しによって、それらが失われないか確認する。
5. 成功事例で確認された機能や振る舞いを、新しい設計でも維持できるか検討する。
6. 維持できない場合は、その理由と必要性を明確にする。
7. 作り直し後の設計が、過去の成功事例で達成した品質を損なわないか検討する。

**過去の成功事例を確認せずに、失敗事例だけを根拠としてスキル全体を作り直してはならない。**

過去の成功事例と現在の問題を両立できる改善方針を優先する。

### 4.4 改善要否の判断

現在のレポートと過去の成功事例を総合的に分析し、改善要否を判断する。

#### eval-skill 評価レポートがある場合

評価レポートから次の情報を確認する。

- 評価結果
- FAILとなった項目
- 再現性に関する問題
- 改善度に関する問題
- 副作用に関する問題
- 評価時に発見された問題
- 具体的な改善提案

FAILや未解決の問題があり、SKILL.mdの修正で解決できる場合は改善が必要と判断する。

評価結果がPASSであっても、レポートに対応すべき問題や改善事項が残っている場合は改善が必要と判断する。

評価結果がNOT EVALUATEDの場合は、評価結果を成功とみなしてはならない。評価できなかった原因を確認し、エージェント自身で解決できる場合は解決を試みる。解決できない場合はユーザーに対応を依頼して停止する。

#### retro KPIレポートがある場合

KPIレポートから次の情報を確認する。

- KPIの達成状況
- 発生した問題
- 問題の原因
- 改善が必要な項目
- 改善提案
- 今後の対応方針

SKILL.mdの修正で解決できる問題や、スキルの動作改善につながる具体的な提案がある場合は改善が必要と判断する。

KPIレポートに記載された改善提案をすべて無条件に採用してはならない。対象スキルの目的や既存仕様、過去の成功事例に照らし合わせて採用可否を判断する。

#### 改善不要と判断する条件

次の条件を満たす場合は改善不要と判断する。

- 現在のレポートに対応すべき問題がない。
- SKILL.mdの修正が必要な改善事項がない。
- 未解決のFAILや改善事項がない。
- 過去の成功事例を損なう変更が必要ない。
- レポートに記載された改善事項がすべて解決済みである。

改善不要と判断した場合はSTEP 11へ進む。

## 5. 改善内容の決定

改善が必要な場合は、修正内容を具体的に決める。

以下を明確にする。

- 発生している問題
- 問題が発生した原因
- 修正するSKILL.mdの箇所
- 修正内容
- 修正によって期待する効果
- 修正によって発生する可能性がある副作用
- 過去の成功事例から維持する仕様・手順
- 過去の成功事例に影響する変更の有無

改善内容は、現在のレポートに記載された問題や提案と対応づける。

過去の成功事例で有効だった仕様や手順は、原則として維持する。

変更が必要な場合は、変更する理由と、従来の成功事例に対する影響を明確にする。

問題の原因が不明な場合は、原因を推測で断定しない。

SKILL.mdの修正だけでは解決できない問題は、無理に修正しない。

## 6. 正式版SKILL.mdの編集

改善内容に基づいて、次のファイルを直接編集する。

`.agents/skills/<skill-name>/SKILL.md`

編集時のルール：

- 既存のYAML Frontmatterを維持する。
- `name` と `description` の整合性を維持する。
- 既存の目的や仕様を不用意に変更しない。
- 指示の曖昧さをなくす。
- 手順、入力、出力、判定条件を明確にする。
- 手順間の矛盾をなくす。
- 同じ内容を重複して記載しない。
- 改善対象と無関係な箇所を変更しない。
- レポートにない機能を追加しない。
- 過去の成功事例で有効だった仕様や手順を維持する。
- 成功事例に影響する変更を行う場合は、その理由と影響を明確にする。

編集後、必ずファイル全体を読み直す。

次の項目を確認する。

- YAML Frontmatterが正しいこと。
- Markdownの構造が正しいこと。
- 指示に矛盾がないこと。
- 必要な手順が欠落していないこと。
- 既存仕様が不必要に失われていないこと。
- 今回の改善内容が反映されていること。
- 過去の成功事例で有効だった機能や振る舞いが維持されていること。
- 大幅な変更の場合、過去の成功事例に対する影響を検討済みであること。

## 7. Git commit

SKILL.mdの編集と確認が完了したら、今回の変更をGit commitする。

commit前に差分を確認する。

```bash
git diff -- .agents/skills/<skill-name>/SKILL.md
git status --short
```

今回編集したSKILL.mdだけをcommit対象とする。

他のファイルにユーザーの変更がある場合、それらを一緒にcommitしてはならない。

commitメッセージは、今回の変更内容が分かる英語で作成する。

例：

```text
Improve <skill-name> skill instructions
```

Git commitの実行に失敗した場合は、エラーメッセージを表示し、ユーザーに手動操作を依頼して停止する。

commitが成功したことを確認してからSTEP 8へ進む。

## 8. eval-skillによる再評価

編集とGit commitが完了したら、`eval-skill` を使用して対象スキルを再評価する。

評価対象は、正式版の次のファイルとする。

`.agents/skills/<skill-name>/SKILL.md`

今回の改善内容だけでなく、既存機能への副作用も評価する。

特に、過去の成功事例で確認された機能や振る舞いが維持されているかを確認する。

評価レポートの保存先は次のとおり。

`docs/eval-reports/<skill-name>/<datetime>.md`

再評価の際は、最新の評価レポートを必ず読み込む。

評価結果を確認し、STEP 9へ進む。

## 9. 再評価結果によるループ判断

再評価結果をもとに、スキルの改善が必要か判断する。

### 9.1 改善が必要な場合

次のいずれかに該当する場合は、改善を続ける。

- 評価結果がFAILである。
- 対応すべき問題が残っている。
- 新たな問題が発見された。
- 既存機能への副作用が発生している。
- 期待する改善効果が得られていない。
- 過去の成功事例で有効だった機能や振る舞いが失われている。

STEP 4に戻り、最新の評価レポートと、必要に応じて最新のKPIレポートおよび過去の成功事例を再確認する。

改善方針を決めた後、STEP 5からSTEP 8まで実行する。

**改善と再評価のループに回数制限は設けない。改善が必要である限り、原則として繰り返す。**

### 9.2 改善不要の場合

次の条件を満たす場合は改善不要と判断する。

- 最新の評価結果がPASSである。
- 対応すべきFAILが残っていない。
- 対応すべき改善事項が残っていない。
- 重大な副作用が発生していない。
- 過去の成功事例で有効だった機能や振る舞いが維持されている。

改善不要と判断した場合はSTEP 11へ進む。

### 9.3 NOT EVALUATEDの場合

NOT EVALUATEDの場合は、改善不要と判断してはならない。

評価できなかった原因を確認する。

エージェント自身で解決できる問題であれば解決を試み、再評価する。

権限不足、実行環境の制約、外部サービスの利用不可など、エージェント自身では解決できない問題の場合は、原因と必要な対応をユーザーに説明して停止する。

## 10. ループの停止条件

改善ループは原則として無制限に継続する。

回数を理由に改善を打ち切ってはならない。

ただし、以下のようなエージェント自身では解決できない問題が発生した場合は停止する。

- 必要なファイルへのアクセス権限がない。
- 必要なGit操作の権限がない。
- 必要なコマンドやツールが利用できない。
- 外部サービスや評価環境が利用できない。
- ユーザーの判断や情報がなければ改善方針を決定できない。
- 既存のユーザー変更と今回の変更を安全に区別できない。
- その他、エージェント自身で安全に解決できない問題がある。

停止する場合は、次の内容をユーザーに報告する。

- 停止した理由
- 発生したエラーや問題
- これまでに実施した作業
- Git commitの実施状況
- 未解決の問題
- ユーザーに必要な対応

未解決の問題がある状態で、改善完了として扱ったりPRを作成したりしてはならない。

## 11. git-create-prの実行

改善不要と判断した場合は、`git-create-pr` スキルを使用する。

PR作成は `git-create-pr` に委任する。

以下の場合は `git-create-pr` を実行してはならない。

- 改善が必要な状態である。
- 最新の評価結果がFAILである。
- 評価結果がNOT EVALUATEDである。
- 改善ループを停止したが、未解決の問題が残っている。
- Git操作に失敗している。
- ユーザーの対応が必要な問題が残っている。

`git-create-pr` の実行結果を確認し、成功・失敗を記録する。

## 12. 禁止事項

以下を禁止する。

- `skill-name` を特定できない状態で改善を開始すること。
- 呼び出し元やレポートから対象スキルを推測して決めること。
- 呼び出し元から渡されたレポートだけを読んで改善判断を完結させること。
- 両方のレポートを確認せず、確認したことにすること。
- 過去の成功事例を確認せずに大幅な変更や作り直しを行うこと。
- 過去の成功事例を理由なく削除・変更すること。
- 2種類のレポートが必須であると扱うこと。
- レポートに記載されていない問題を推測で作ること。
- 正式版SKILL.md以外を編集して改善完了とすること。
- ユーザーの既存変更を破棄すること。
- 対象外のファイルを一緒にcommitすること。
- SKILL.mdの編集後にGit commitを省略すること。
- Git commit前に再評価へ進むこと。
- 評価結果がFAILまたはNOT EVALUATEDの状態でPRを作成すること。
- 改善が必要な状態でPRを作成すること。
- ループ回数の上限を設けること。
- エージェント自身で解決できない問題を無視して処理を続けること。

## 13. 完了報告

処理完了後、以下を報告する。

### 13.1 改善内容

- 呼び出し元スキル名
- 対象スキル名
- 改善対象ファイル
- 参照したKPIレポート
- 参照した評価レポート
- 参照した過去の成功事例
- 発見した問題
- 実施した改善内容
- 過去の成功事例を維持するために行った対応

### 13.2 評価結果

- 最終評価結果
- 評価レポートの保存先
- 未解決の問題の有無

### 13.3 Git情報

- 作業ブランチ
- 作成したcommit
- PR作成結果
- PR URL（取得できた場合）

### 13.4 最終状態

次のいずれかを明記する。

- `SUCCESS`: 改善・再評価が完了し、改善不要と判断され、PR作成まで完了した。
- `PARTIAL`: 改善や評価の途中で、ユーザー対応が必要な問題により停止した。
- `FAILED`: 処理を開始できない、または重大なエラーによって処理が失敗した。

PR作成に失敗した場合は、改善・評価が完了していても `SUCCESS` としてはならない。
