# eval-skill

## 1. 目的

スキルの改善によって、既存の問題が解消され、かつ新しい問題が発生していないことを検証する。

評価は、実際のタスクを想定したドライランによって実施する。

評価に使用する疑似タスクは、評価対象スキルの目的・適用範囲・仕様を分析したうえで、エージェント自身が3件作成する。

評価者の主観や推測ではなく、確認できた事実と出力結果に基づいて判定する。

評価結果に応じて、次の処理を行う。

- 改善が必要な場合：`improve-skill` を呼び出す。
- 改善不要の場合：`git-create-pr` を使用する。
- 評価不能の場合：不足情報や問題の解決を試み、解決できなければ停止する。

## 2. 起動トリガー

本スキルは、主に他のスキルから評価を依頼された場合に実行する。

### 2.1 create-skillからの呼び出し

`create-skill` が新しいスキルを作成した後、評価を依頼する場合に呼び出される。

評価対象のスキル名または定義ファイルのパスを受け取り、評価を実施する。

### 2.2 improve-skillからの呼び出し

`improve-skill` が正式版のSKILL.mdを編集し、Git commitした後、再評価を依頼する場合に呼び出される。

再評価では、初回評価で作成した疑似タスクと期待結果を原則としてそのまま使用する。

改善によって新しい問題が発生していないか、既存の成功していた動作が維持されているかを重点的に確認する。

### 2.3 直接呼び出し

ユーザーから直接評価を依頼された場合も実行できる。

ただし、通常の起動経路は `create-skill` または `improve-skill` からの呼び出しとする。

## 3. 入力

以下を入力として受け取る。

| 入力 | 必須 | 説明 |
|---|---|---|
| 評価対象スキル | 必須 | スキル名または定義ファイルのパス |
| 呼び出し元 | 任意 | `create-skill`、`improve-skill`、ユーザーなど |
| 旧版 | 任意 | 比較対象となる旧版のSKILL.md |
| 初回評価レポート | 任意 | 再評価時に使用する初回評価レポートのパス |
| 改善履歴 | 任意 | 改善内容や過去の評価結果を記録した情報 |

### 3.1 入力不足時のルール

- 評価対象スキルが特定できない場合は、評価を開始しない。
- 旧版が存在しない場合は、改善度の比較評価を実施できないため、改善度を `NOT EVALUATED` とする。
- 改善履歴が存在しない場合は、旧版と新版の差分から改善対象を特定する。
- 入力内容が不明確な場合、推測で補完しない。
- 疑似タスクの作成に必要な情報が不足している場合は、その不足内容を報告する。
- 再評価時に初回評価レポートを特定できない場合は、過去の評価レポートを調査する。
- 再評価で初回の疑似タスクを復元できない場合は、別のタスクで代用して評価を続けてはならない。

### 3.2 評価対象の特定

評価対象のスキル名を `<skill-name>` とする。

評価対象ファイルは原則として次のパスとする。

`.agents/skills/<skill-name>/SKILL.md`

別のパスが明示的に指定された場合は、そのパスを評価対象として扱う。

評価対象のスキル名を特定できない場合は、ユーザーまたは呼び出し元に確認する。

## 4. 評価の基本ルール

評価中は以下のルールを必ず守る。

1. 評価用の疑似タスクは、エージェント自身が必ず3件作成する。
2. 3件の疑似タスクは、異なる評価観点を持つものとする。
3. すべての疑似タスクに対して、同一の評価手順を適用する。
4. 旧版と新版の比較では、タスクの入力条件を同一にする。
5. スキル以外の実行条件は、可能な限り統一する。
6. 評価対象スキルに記載されていない手順を、評価者の判断で追加しない。
7. 確認できない項目をPASSにしない。
8. 実行していないテストを、実行済みとして報告しない。
9. 評価中にスキル定義を変更しない。
10. 期待する結果が定義されていない場合は、期待結果を推測せず、その旨を記録する。
11. 各判定には、根拠となる出力、ファイル、行番号、または実行結果を記載する。
12. 疑似タスクの作成時点で、評価対象スキルの実装や内部処理を不当に誘導する条件を追加しない。
13. 過去に成功した動作や仕様を、評価対象から不用意に除外しない。
14. 再評価では初回評価と同じ疑似タスク、入力条件、期待結果を使用する。
15. 評価結果がPASSであっても、評価できていない項目を隠してはならない。

## 5. 評価手順

### STEP 1. 評価対象の確認

以下を確認する。

- 評価対象スキルのファイルが存在する。
- スキルの目的と適用範囲が明確である。
- 入力と出力が定義されている。
- 実行手順が記載されている。
- 制約事項や禁止事項が記載されている。
- 旧版と新版を区別できる。
- 呼び出し元から評価依頼の目的が渡されている場合、その内容を把握している。

確認結果を記録する。

評価対象ファイルが存在しない場合は、評価を開始せず、その理由を報告する。

### STEP 2. 過去の評価結果・改善履歴の確認

疑似タスクを作成する前に、対象スキルに関する過去の評価結果や改善履歴を確認する。

確認する情報：

- 過去の評価レポート
- 過去のKPIレポート
- 過去にPASSとなった評価項目
- 過去に正常動作が確認された処理
- 過去に発生した不具合
- 不具合の再現条件
- 過去の改善内容
- 改善によって解消された問題
- 改善によって新たに発生した問題

評価レポートの保存先：

`docs/eval-reports/<skill-name>/`

KPIレポートの保存先：

`docs/retro-reports/<skill-name>/`

関連するレポートが存在する場合は、最新のものだけでなく、今回の評価に関係する過去のレポートも確認する。

特に、過去にPASSとなった評価項目やKPIを達成した実行事例は、正常動作を確認するための重要な情報として扱う。

過去の成功事例を確認せずに、現在の問題だけを根拠として評価対象の仕様や期待結果を変更してはならない。

過去の成功事例が見つからない場合は、その事実を記録する。

### STEP 3. 疑似タスクの作成

評価対象スキルの内容を分析し、ドライランに使用する疑似タスクをエージェント自身が3件作成する。

疑似タスクは、スキルが想定する実際の利用状況を再現できる内容にする。

#### 3.1 疑似タスクの作成方針

以下の3つの観点から、それぞれ1件ずつ作成する。

| ID | 評価観点 | 目的 |
|---|---|---|
| TC-01 | 通常動作 | スキルの主目的に沿った標準的なタスクを正常に処理できるか確認する |
| TC-02 | 境界条件・例外条件 | 不完全な入力、特殊な条件、制約事項などに適切に対応できるか確認する |
| TC-03 | 応用・複合条件 | 複数の要件や異なる条件が組み合わさったタスクを適切に処理できるか確認する |

ただし、スキルの性質上、上記の観点が適切でない場合は、スキルの目的に合わせて評価観点を調整してよい。

その場合も、必ず異なる3つの観点から疑似タスクを作成する。

#### 3.2 改善履歴の反映

旧版で発生した不具合や改善履歴が存在する場合は、以下を守る。

- 旧版で発生した不具合の再現条件を、最低1件の疑似タスクに含める。
- 改善履歴に記載された修正内容を検証できる条件を含める。
- 改善対象だけに偏らず、通常動作や改善対象外の動作も評価できるようにする。
- 過去に正常動作が確認された重要な処理や仕様を、回帰確認の対象に含める。
- 過去にPASSとなった評価項目を、可能な限り疑似タスクの期待結果に反映する。

#### 3.3 過去の成功事例の回帰確認

過去の評価レポートやKPIレポートに成功事例が記録されている場合は、その成功事例が新版でも維持されているか確認できるようにする。

特に次の点を重視する。

- 過去に正常動作した入力条件
- 過去に期待どおりの出力が得られた処理
- 過去に評価でPASSとなった重要な仕様
- 過去の改善で解決した問題
- 過去に安定して実行できていた手順

現在の改善対象だけを検証する疑似タスク構成にしてはならない。

過去の成功事例を維持できているか確認することも、評価の重要な目的とする。

#### 3.4 疑似タスクの定義

各疑似タスクについて、以下を明確にする。

- タスクID
- タスク名
- 評価観点
- 疑似タスクの内容
- 入力条件
- 期待される動作
- 期待される出力
- 確認すべき項目
- 旧版で発生した問題との関連性（該当する場合）
- 過去の成功事例との関連性（該当する場合）

#### 3.5 疑似タスク作成時の禁止事項

- 評価対象スキルの仕様に存在しない機能を要求しない。
- 実際の利用状況から大きく逸脱した条件を設定しない。
- 期待結果を評価者の好みで決定しない。
- 3件の疑似タスクに実質的に同じ内容を使用しない。
- 旧版と新版で異なる入力条件を使用しない。
- 評価対象スキルの内部実装を不必要に指定しない。
- 過去の成功事例を理由なく評価対象から除外しない。

#### 3.6 疑似タスク作成の確認

3件の疑似タスクを作成した後、以下を確認する。

1. 3件すべてが評価対象スキルの適用範囲内である。
2. それぞれ異なる評価観点を持っている。
3. 各タスクの入力条件が明確である。
4. 各タスクの期待結果を明確に定義できる。
5. 改善履歴が存在する場合、改善対象を検証できるタスクが含まれている。
6. 過去の成功事例が存在する場合、その正常動作を確認できるタスクが含まれている。
7. 改善対象外の既存動作も確認できる。

確認できない項目がある場合は、その理由を記録する。

3件の疑似タスクを作成できない場合は、無理に評価を進めず、不足している情報を報告する。

### STEP 4. 旧版のドライラン

旧版が存在する場合、STEP 3で作成した3件の疑似タスクすべてに旧版スキルを適用する。

以下を記録する。

- 実行された手順
- 各手順の出力
- 期待結果との一致・不一致
- 発生した問題
- 問題の発生箇所

旧版のドライラン結果を、新版との比較基準とする。

旧版が存在しない場合は、このSTEPをスキップする。

旧版が存在しない場合でも、過去の評価レポートやKPIレポートに記録された成功事例を、回帰確認の参考情報として使用する。

### STEP 5. 新版のドライラン

STEP 3で作成した同一の3件の疑似タスクすべてに新版スキルを適用する。

すべてのタスクで以下を記録する。

1. スキルの手順に従って実行できたか。
2. 手順の解釈に曖昧さがなかったか。
3. 期待する出力が生成されたか。
4. 出力形式と内容が仕様を満たしているか。
5. 禁止事項や制約事項に違反していないか。
6. 予期しない動作が発生していないか。
7. 過去に成功していた動作が維持されているか。

タスクごとに結果を保存する。

### STEP 6. 3つの評価軸による評価

以下の3軸を、それぞれ独立して評価する。

#### 6.1 再現性（Reproducibility）

目的：異なる疑似タスクに対して、同じスキルが一貫した手順と品質で動作することを確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| R1 | 手順の一貫性 | すべてのタスクで定義された手順が実行される |
| R2 | 入力条件への対応 | 対象範囲内の入力に対して適切に処理できる |
| R3 | 出力形式の一貫性 | すべてのタスクで指定された出力形式を満たす |
| R4 | 判断基準の一貫性 | 同じ条件に対して矛盾する判断をしない |
| R5 | 手順の明確性 | 実行に必要な判断を、未定義の推測に依存しない |

判定ルール：

- すべてのチェック項目がPASSの場合、再現性をPASSとする。
- 1つでもFAILがあれば、再現性をFAILとする。
- 確認できない項目がある場合はNOT EVALUATEDとする。

#### 6.2 改善度（Improvement）

目的：旧版で発生していた問題が新版で解消されていることを確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| I1 | 既知不具合の解消 | 旧版で発生した問題が新版で再発しない |
| I2 | 修正内容の反映 | 改善履歴に記載された修正がスキルに反映されている |
| I3 | 期待動作の実現 | 改善対象のタスクで期待結果が得られる |
| I4 | 回帰の防止 | 旧版で正常だった動作が新版でも維持される |

判定ルール：

- すべてのチェック項目がPASSの場合、改善度をPASSとする。
- 1つでもFAILがあれば、改善度をFAILとする。
- 旧版が存在しない場合はNOT EVALUATEDとする。
- 比較対象となる不具合や期待動作が特定できない場合もNOT EVALUATEDとする。

#### 6.3 副作用（Side Effects）

目的：改善によって新しい問題や予期しない動作が発生していないことを確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| S1 | 既存機能への影響 | 改善対象外の既存動作が維持されている |
| S2 | 過剰な処理 | 不必要な処理や手順が追加されていない |
| S3 | 入力範囲への影響 | 従来対応できていた入力が拒否されていない |
| S4 | 出力への影響 | 意図しない出力の欠落や変更がない |
| S5 | 安全性 | 権限逸脱、データ破壊、機密情報の漏洩などの問題がない |
| S6 | 制約事項 | スキルの適用範囲や禁止事項が守られている |

判定ルール：

- すべてのチェック項目がPASSの場合、副作用をPASSとする。
- 1つでもFAILがあれば、副作用をFAILとする。
- 検証できない項目がある場合はNOT EVALUATEDとする。

## 6. 評価結果の判定

各評価軸は以下の3種類で判定する。

| 判定 | 意味 |
|---|---|
| PASS | すべてのチェック項目が合格 |
| FAIL | 1つ以上のチェック項目で不合格 |
| NOT EVALUATED | 必要な情報や検証結果が不足している |

### 6.1 総合評価

以下のルールを厳守する。

| 再現性 | 改善度 | 副作用 | 総合評価 |
|---|---|---|---|
| PASS | PASS | PASS | PASS |
| FAIL | 任意 | 任意 | FAIL |
| 任意 | FAIL | 任意 | FAIL |
| 任意 | 任意 | FAIL | FAIL |
| NOT EVALUATED | 任意 | 任意 | NOT EVALUATED |
| 任意 | NOT EVALUATED | 任意 | NOT EVALUATED |
| 任意 | 任意 | NOT EVALUATED | NOT EVALUATED |

FAILが1つでも存在する場合は、NOT EVALUATEDよりFAILを優先する。

NOT EVALUATEDが1つでも存在し、FAILがない場合は、総合評価をNOT EVALUATEDとする。

### 6.2 判定上の禁止事項

- 一部のPASSを理由に、全体をPASSにしない。
- 重大な問題を、軽微な問題として扱わない。
- 根拠がない場合にPASSと判定しない。
- テスト未実施をPASSとして扱わない。
- 評価者の期待や好みを判定基準にしない。
- 過去の成功事例が失われていることを無視しない。
- 評価できなかった項目を、問題なしとして扱わない。

## 7. 評価レポートの作成

評価結果を以下のパスにMarkdown形式で出力する。

`docs/eval-reports/<skill-name>/<datetime>.md`

`<datetime>` はレポート作成時のローカル時刻を使用し、次の形式とする。

`YYYYMMDD_HHMMSS`

例：

`docs/eval-reports/example-skill/20261119_103000.md`

出力ディレクトリが存在しない場合は作成する。

同じ日時のファイルが既に存在する場合は、既存ファイルを上書きせず、別の日時を使用して保存する。

- 次回評価で確認すべき項目：

## 11. 次のアクション

- 判定：
- 呼び出すスキル：
- 呼び出し理由：
- 未解決事項：

## 8. 評価結果のフィードバック

評価レポートの作成後、評価結果を呼び出し元に返す。

以下の情報を必ず返す。

1. 総合評価
2. 各評価軸の判定
3. 発見された問題
4. 問題の根拠
5. 改善提案
6. 過去の成功事例が維持されているか
7. 次回評価で確認すべき項目
8. 評価レポートの保存先

### 8.1 総合評価がPASSの場合

- 評価結果を呼び出し元に返す。
- 検証済みの変更を維持する。
- 対応すべき未解決の問題がないことを確認する。
- 改善不要と判断し、STEP 9へ進む。

### 8.2 総合評価がFAILの場合

- FAILとなった項目を明示する。
- 問題の発生条件と根拠を返す。
- 改善案の再検討を要求する。
- `improve-skill` を呼び出す。
- 評価レポートの保存先を `improve-skill` に渡す。
- 修正後は同じ3件の疑似タスクで再評価する。

### 8.3 総合評価がNOT EVALUATEDの場合

- 評価できなかった項目を明示する。
- 不足している入力や検証条件を返す。
- 不足情報をエージェント自身で補完できる場合は、補完して再評価する。
- ユーザーや呼び出し元の判断が必要な場合は、その内容を伝えて停止する。
- NOT EVALUATEDを改善不要として扱ってはならない。
- `improve-skill` や `git-create-pr` を実行してはならない。

## 9. 次の処理の決定

評価結果に応じて、次のスキルを使用する。

### 9.1 改善が必要な場合

総合評価がFAILの場合、または評価結果に対応すべき改善事項が残っている場合は、`improve-skill` を呼び出す。

呼び出し時には以下を渡す。

- `skill-name`：評価対象のスキル名
- `eval-report`：今回作成した評価レポートのパス
- `evaluation-result`：総合評価
- `issues`：発見された問題
- `improvement-suggestions`：改善提案
- `preserve-items`：維持すべき過去の成功事例や正常動作

`improve-skill` は、KPIレポートと評価レポートの両方を可能な限り確認して改善判断を行う。

### 9.2 改善不要の場合

総合評価がPASSであり、対応すべき問題や改善事項が残っていない場合は、`git-create-pr` スキルを使用する。

PR作成は `git-create-pr` に委任する。

呼び出し時には、以下の情報を渡す。

- `skill-name`：評価対象のスキル名
- `eval-report`：今回作成した評価レポートのパス
- `evaluation-result`：PASS
- `summary`：評価結果の概要

**評価結果がPASSであることだけでなく、対応すべき未解決事項がないことを確認してからPR作成へ進む。**

### 9.3 評価不能の場合

総合評価がNOT EVALUATEDの場合は、改善不要と判断してはならない。

不足情報や評価環境の問題を確認し、エージェント自身で解決できる場合は解決を試みる。

解決できない場合は、原因と必要な対応を呼び出し元またはユーザーに報告して停止する。

NOT EVALUATEDの状態で `improve-skill` や `git-create-pr` を呼び出してはならない。

## 10. 再評価時のルール

`improve-skill` から再評価を依頼された場合は、以下のルールを守る。

1. 初回評価レポートを読み込む。
2. 初回評価で作成した3件の疑似タスクを取得する。
3. 初回評価と同じ入力条件を使用する。
4. 初回評価と同じ期待結果を使用する。
5. 初回評価と同じ評価基準を使用する。
6. 旧版と新版を区別して評価する。
7. 改善内容が反映されているか確認する。
8. 過去に成功していた動作が維持されているか確認する。
9. 新たな副作用が発生していないか確認する。
10. 新しい評価レポートを作成する。

再評価のために、評価基準や期待結果を変更してPASSにしてはならない。

初回評価で作成した疑似タスクが取得できない場合は、推測で再作成して同一条件の評価と扱ってはならない。

必要な情報を復元できない場合は、NOT EVALUATEDとし、その理由を報告する。

再評価でも評価レポートの保存先は次のとおりとする。

`docs/eval-reports/<skill-name>/<datetime>.md`

各評価レポートは別々のファイルとして保存し、過去のレポートを上書きしない。

## 11. 最終ルール

- 評価は必ず本スキルに定義された基準に従う。
- 評価基準を実行途中で変更しない。
- 疑似タスクは必ず3件作成する。
- 疑似タスクは評価対象スキルの目的と適用範囲に基づいて作成する。
- 旧版と新版には同一の疑似タスクを適用する。
- 再評価時は初回評価で作成した疑似タスクを再利用する。
- すべての判定に根拠を記載する。
- 未実施のテストを実施済みと報告しない。
- 評価結果と改善提案を混同しない。
- 過去の成功事例や正常動作を評価対象から不用意に除外しない。
- 総合評価がPASSになるまで、改善完了と判断しない。
- FAILの場合は `improve-skill` を使用する。
- PASSで改善不要の場合は `git-create-pr` を使用する。
- NOT EVALUATEDの場合は改善不要と判断せず、問題を解決できなければ停止する。
