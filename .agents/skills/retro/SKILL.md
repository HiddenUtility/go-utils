# retro

## 1. 目的

業務スキルの実行結果を振り返り、今後のスキル改善や品質向上に利用できる情報を記録する。

本スキルの責務は以下のとおりとする。

1. 業務スキルの実行結果を分析する。
2. Keep / Problem / Try（KPT）を抽出する。
3. 根拠付きの振り返りレポートを作成・保存する。
4. 業務スキル自体に改善が必要か判断する。
5. 改善が必要な場合はimprove-skillを呼び出す。
6. 改善が不要な場合はgit-create-prを呼び出す。
7. 処理結果を呼び出し元またはユーザーに報告する。

本スキル自身は業務スキルの実装や修正を行わない。

後続スキルの呼び出しは、KPTレポートの作成と保存が完了した後にのみ実施する。

## 2. トリガー

以下の条件を満たした場合に実行する。

- 業務スキルが実行された。
- 業務スキルの実行結果が存在する。
- ユーザーまたは呼び出し元から本スキルが明示的に呼び出された。

### 2.1 実行対象外

以下の場合は通常の振り返りを実行しない。

- 業務スキルが実行途中で終了した。
- 業務スキルが失敗し、完了条件を満たしていない。
- ユーザーが作業の中止を要求した。
- 業務スキルの実行結果が存在しない。

ただし、失敗した作業についてユーザーまたは呼び出し元が明示的に振り返りを要求した場合は実行してよい。

実行対象外の場合は、その理由を報告して終了する。

## 3. 呼び出し方法

本スキルは、ユーザーからの直接呼び出しと、他のスキルからの呼び出しの両方に対応する。

### 3.1 User Invocation

ユーザーが直接呼び出した場合は、以下の情報を確認する。

| 入力 | 必須 | 説明 |
|---|---|---|
| 業務スキル名 | 必須 | 振り返り対象のスキル名 |
| 実行結果 | 必須 | 実施内容、変更内容、実行結果 |
| 実行ログ | 推奨 | コマンド出力、操作履歴、エラーなど |
| ドライラン評価レポート | 任意 | eval-skillが生成した評価レポート |
| 改善前の問題 | 任意 | 作業開始時に確認されていた問題 |

情報が不足している場合は、必要な情報だけをユーザーに質問する。

既に提供されている情報を再質問しない。

### 3.2 Skill Invocation

他のスキルから呼び出された場合は、呼び出し元から渡された情報を使用する。

受け取る情報：

| 入力 | 必須 | 説明 |
|---|---|---|
| Skill Name | 必須 | 実行した業務スキル名 |
| Execution Result | 必須 | 実施内容、変更内容、実行結果 |
| Execution Logs | 推奨 | コマンド出力、操作履歴、エラーなど |
| Evaluation Report | 任意 | eval-skillが生成した評価レポート |
| Previous Problems | 任意 | 作業開始時に確認されていた問題 |
| Additional Context | 任意 | その他の関連情報 |

以下のルールに従う。

1. 呼び出し元から渡された情報を最優先する。
2. 不足情報は実行ログや関連ファイルから取得する。
3. 呼び出し元から渡された情報をユーザーに再質問しない。
4. 必要な情報が不足している場合のみ、呼び出し元に確認する。
5. 取得できなかった情報は「未取得」と記録する。
6. 同一タスクに関係しないログを混在させない。
7. 処理結果を呼び出し元に返す。

呼び出し元が不明な場合は、ユーザーからの直接呼び出しとして扱う。

## 4. 入力の取得ルール

以下の情報を確認する。

1. 業務スキルの実行ログ
2. ドライラン評価レポート（存在する場合）
3. 業務スキルが生成した成果物
4. 作業開始時の問題や要求事項

取得ルール：

- 呼び出し元から渡された情報を最優先する。
- ログの場所が不明な場合は、プロジェクト内の関連ログを検索する。
- 存在しないログや評価レポートを推測で作成しない。
- 取得できなかった情報は「未取得」と記録する。
- 複数の資料で情報が矛盾する場合は、実際の実行結果を優先する。
- 矛盾した内容も必要に応じて記録する。
- ドライラン評価レポートが存在しない場合も、実行ログをもとにKPTを作成してよい。

## 5. 振り返り手順

### STEP 1. 実行内容の確認

以下を確認する。

- 実行した業務スキル
- 作業の目的
- 実施した作業
- 変更したファイル
- 実行したテスト
- テスト結果
- 発生したエラーや問題
- 最終的な完了状態

確認できた事実と推測を区別する。

### STEP 2. 関連資料の確認

以下の資料を確認する。

1. 業務スキルの実行ログ
2. ドライラン評価レポート（存在する場合）
3. 業務スキルが生成した成果物
4. 作業開始時の問題や要求事項

資料間に矛盾がある場合は、その内容を記録する。

### STEP 3. KPTの抽出

実行結果からKeep / Problem / Tryを抽出する。

#### 3.1 Keep（継続すること）

今後も維持すべき有効な手順、設計、判断、仕組みを記録する。

抽出条件：

- 期待した結果が得られた。
- 作業効率や品質の向上につながった。
- 問題の予防や早期発見に役立った。
- 他の類似タスクにも適用できる。

単に実施しただけで効果が確認できない作業はKeepに含めない。

#### 3.2 Problem（問題点）

作業中に発生した問題、非効率な手順、判断の誤り、不足していた情報を記録する。

抽出条件：

- 期待した結果が得られなかった。
- 作業に余計な時間や手戻りが発生した。
- 手順や仕様が曖昧だった。
- テストや確認が不足していた。
- スキルの指示と実際の動作に不一致があった。
- 評価レポートでFAILとなった項目が存在した。

問題が発生しなかった場合は「顕著な問題なし」と記録する。

#### 3.3 Try（次回試すこと）

Problemを解消するために、次回以降に実施する具体的な改善策を記録する。

抽出条件：

- Problemを解消できる。
- 実行可能な具体的な行動である。
- 改善対象と改善内容が明確である。
- 類似タスクで再利用できる。

Tryは可能な限りProblemと対応付ける。

Problemが存在しない場合でも、効果が確認された改善案があればTryとして記録してよい。

### STEP 4. KPTの品質確認

抽出したKPTについて、以下を確認する。

| ID | チェック項目 | PASS条件 |
|---|---|---|
| K1 | 事実との整合性 | 実行結果やログに根拠がある |
| K2 | 分類の適切性 | Keep / Problem / Tryの定義に合致する |
| K3 | 具体性 | 内容が具体的で理解できる |
| K4 | 重複の排除 | 同じ内容が複数項目に重複していない |
| K5 | 改善可能性 | Tryが実行可能な改善行動になっている |

判定ルール：

- すべてPASSの場合、KPTを確定する。
- FAILがある場合、該当項目を修正して再確認する。
- 根拠のない内容は削除するか「仮説」と明記する。

### STEP 5. KPTレポートの作成・保存

振り返り結果をMarkdownファイルとして保存する。

**保存先は必ずGitリポジトリのルート直下にある以下のディレクトリとする。**

```text
docs/retro-reports/<skill-name>/<datetime>.md
```

保存先を変更してはならない。

#### 5.1 Gitリポジトリのルートを取得

最初に以下のコマンドを実行する。

```bash
git rev-parse --show-toplevel
```

標準出力からGitリポジトリのルートディレクトリを取得し、`REPOSITORY_ROOT` とする。

保存先は以下のように決定する。

```text
REPOSITORY_ROOT/docs/retro-reports/<skill-name>/
```

保存先は絶対パスで扱う。

以下を基準にしてはならない。

- 現在の作業ディレクトリ
- Codexを起動したときのディレクトリ
- retroスキルの配置ディレクトリ
- 業務スキルの配置ディレクトリ

Gitリポジトリのルートを取得できない場合は、保存先を推測してはならない。

エラー内容を記録し、ユーザーまたは呼び出し元に報告して処理を停止する。

別のディレクトリに代替出力してはならない。

#### 5.2 skill-nameの決定

`<skill-name>` には振り返り対象となる業務スキルの名前を使用する。

例：

```text
docs/retro-reports/git-create-branch/
docs/retro-reports/git-create-pr/
docs/retro-reports/create-skill/
```

ルール：

- 実際のスキル名を使用する。
- スキル名は小文字の英数字とハイフンを基本とする。
- スキル名を勝手に別の名前に変更しない。
- スキル名が取得できない場合は、推測せず確認する。
- 同じスキルのレポートは同じディレクトリに保存する。

#### 5.3 保存先ディレクトリの作成

以下のディレクトリを作成する。

```text
REPOSITORY_ROOT/docs/retro-reports/<skill-name>/
```

作成ルール：

1. ディレクトリが存在しない場合は新規作成する。
2. 既に存在する場合は、そのディレクトリを使用する。
3. 既存のディレクトリやファイルを削除してはならない。
4. 指定した保存先以外に同名のディレクトリを作成してはならない。

ディレクトリ作成には以下を使用してよい。

```bash
mkdir -p "${REPOSITORY_ROOT}/docs/retro-reports/<skill-name>"
```

#### 5.4 ファイル名の決定

ファイル名は以下の形式とする。

```text
YYYYMMDD-HHMMSS.md
```

例：

```text
20261119-093015.md
```

ルール：

- 日時はレポート作成時点のローカル時刻を使用する。
- 24時間表記とする。
- 拡張子は `.md` とする。
- ファイル名の先頭に `retro_` などの接頭辞を追加しない。
- 既存ファイルを上書きしてはならない。

同じファイル名が既に存在する場合は、連番を付けて別のファイル名にする。

例：

```text
20261119-093015-01.md
20261119-093015-02.md
```

#### 5.5 ファイルの作成

ファイルの絶対パスを以下の形式で決定する。

```text
REPOSITORY_ROOT/docs/retro-reports/<skill-name>/YYYYMMDD-HHMMSS.md
```

ファイル作成時は、決定済みの絶対パスを使用する。

相対パスを保存先として使用してはならない。

作成ルール：

- Markdown形式で作成する。
- 指定された保存先以外にファイルを作成しない。
- 既存ファイルを上書きしない。
- 実行内容とKPTを対応付ける。
- 根拠のない内容を記載しない。
- 以下の必須構成に従う。

#### 5.6 KPTレポートの必須構成

以下の構成を使用する。

```markdown
# Retrospective Report

## 1. 基本情報

- 実行スキル：
- 実行日時：
- 振り返り日時：
- 実行結果：
- 関連ログ：
- 評価レポート：

## 2. 実行概要

- 作業目的：
- 実施内容：
- 変更したファイル：
- テスト結果：
- 完了状態：

## 3. Keep（継続すること）

| ID | 内容 | 効果 | 根拠 |
|---|---|---|---|
| K-01 | | | |

該当事項がない場合は「該当なし」と記載する。

## 4. Problem（問題点）

| ID | 内容 | 影響 | 発生原因 | 根拠 |
|---|---|---|---|---|
| P-01 | | | | |

該当事項がない場合は「顕著な問題なし」と記載する。

## 5. Try（次回試すこと）

| ID | 対応するProblem | 改善内容 | 期待効果 | 優先度 |
|---|---|---|---|---|
| T-01 | P-01 | | | |

該当事項がない場合は「改善提案なし」と記載する。

優先度：

- HIGH：品質や安全性に重大な影響がある。
- MEDIUM：作業効率や品質の改善に有効である。
- LOW：軽微な改善または将来的な改善である。

## 6. 総括

- 継続すべきこと：
- 解決すべき問題：
- 次回実施する改善：

## 7. スキル改善判定

- 改善対象スキル：
- スキル自体の改善要否：
- 改善が必要な理由：
- 改善対象：
- 対応するProblem：
- 対応するTry：
- 判定根拠：

## 8. 後続処理

- 呼び出し対象：
- 呼び出し理由：
- 呼び出し結果：
- 後続処理の結果：
- 未解決事項：
```

後続処理を実行する前にレポートを作成するため、初回保存時点では「未実施」と記録する。

後続スキルの呼び出し結果が確定した後、この章を更新する。

#### 5.7 保存結果の検証

ファイルを作成したら、必ず以下を検証する。

1. 作成したファイルが実際に存在すること。
2. ファイルの絶対パスを取得できること。
3. ファイルの絶対パスが `REPOSITORY_ROOT/docs/retro-reports/<skill-name>/` の配下にあること。
4. ファイル名が指定形式であること。
5. ファイルの拡張子が `.md` であること。
6. ファイルを読み直し、内容が正しく保存されていること。
7. 必須の章・項目がすべて存在すること。

ファイルを作成しただけで成功と判断してはならない。

実際に作成されたファイルの絶対パスを確認すること。

保存場所が間違っていた場合は、誤って作成したファイルを正しい場所に移動し、保存結果を再確認する。

誤った場所に作成したファイルが不要になった場合は、そのファイルだけを削除してよい。他のファイルやディレクトリを削除してはならない。

正しい場所への保存を確認できない場合は、成功と報告してはならない。

### STEP 6. スキル品質の改善要否を判定

KPTと実行結果をもとに、業務スキル自体の改善が必要か判定する。

**重要：ProblemやTryが存在することだけを理由に、スキル改善が必要と判断してはならない。**

以下の基準で判断する。

#### 6.1 改善が必要な場合

以下のいずれかに該当する場合は、スキル自体の改善が必要と判断する。

- スキルの指示が曖昧で、誤った動作や判断が発生した。
- スキルに必要な手順や確認項目が不足していた。
- エラー処理や異常系の対応が不足していた。
- スキルの実行によって不要な手戻りが発生した。
- スキルの仕様と期待する動作に不一致があった。
- eval-skillの評価結果にFAILがあり、スキルの修正が必要である。
- 同様の問題を再発防止するためにスキルの定義変更が必要である。

この場合、判定結果を「改善あり」とする。

#### 6.2 改善が不要な場合

以下の場合は、スキル自体の改善は不要と判断する。

- スキルの手順と動作に問題がない。
- 発生した問題がスキルの定義変更では解決しない。
- Problemが存在しない。
- Tryが作業上の注意や一時的な対応だけである。
- 改善案が既存のスキル仕様で対応可能である。
- 評価結果にFAILがなく、改善を必要とする根拠がない。

この場合、判定結果を「改善なし」とする。

#### 6.3 判断できない場合

改善要否を判断するための情報が不足している場合は、推測で判定してはならない。

ユーザーからの直接呼び出しの場合は、ユーザーに確認する。

スキルからの呼び出しの場合は、呼び出し元に確認する。

確認が取れるまで後続スキルを呼び出してはならない。

### STEP 7. 後続スキルとの連携

本STEPは、KPTレポートの作成・保存と、スキル品質の改善要否判定が完了した後にのみ実行する。

後続処理は、判定結果によって分岐する。

```text
                 retro
                   |
            KPTレポート作成
                   |
             品質改善の判定
                   |
             改善が必要か？
                /      \
              Yes       No
               |         |
         improve-skill  git-create-pr
               |         |
         改善プロセス    PR作成
```

#### 7.1 改善が必要な場合

改善が必要と判定した場合は、improve-skillを呼び出す。

呼び出し時には以下の情報を渡す。

1. 改善対象のスキル名
2. 改善対象のスキルファイルパス
3. KPTレポートの絶対パス
4. Problemの内容
5. 対応するTryの内容
6. 改善が必要と判断した理由
7. ドライラン評価レポートのパス（存在する場合）

呼び出しルール：

- KPTの内容を勝手に変更して渡してはならない。
- ProblemとTryの対応関係を維持する。
- 改善対象と無関係なスキルを変更させない。
- retro自身でスキルを修正しない。
- improve-skillの呼び出し結果を確認する。
- improve-skillが呼び出せない場合は、その理由を記録する。

**改善が必要な場合、retroからgit-create-prを直接呼び出してはならない。**

improve-skillに後続処理の判断を委ねる。

improve-skillは、自身の処理結果に応じてeval-skillやgit-create-prなどの後続処理を制御する。

retroはimprove-skillの処理を勝手に代行しない。

#### 7.2 改善が不要な場合

改善が不要と判定した場合は、git-create-prを呼び出す。

呼び出し時には以下の情報を渡す。

1. 実行した業務スキル名
2. KPTレポートの絶対パス
3. 作業内容の概要
4. 変更内容の概要
5. 関連Issue番号（確認できた場合のみ）
6. PR作成に必要な追加情報（存在する場合）

呼び出しルール：

- git-create-prを明示的に指定して呼び出す。
- KPTレポートをPRの変更内容に含める。
- PRのタイトルと本文はgit-create-prの仕様に従う。
- retro自身でPRを作成しない。
- retro自身でcommitやpushを行わない。
- 既存PRがある場合はgit-create-prの結果に従う。
- git-create-prの呼び出し結果を確認する。

#### 7.3 後続スキルの失敗

後続スキルの呼び出しに失敗した場合は、以下を実施する。

1. 失敗したスキル名を記録する。
2. 失敗した理由を記録する。
3. KPTレポートを削除しない。
4. 失敗を成功として報告しない。
5. ユーザーまたは呼び出し元に失敗を報告する。

後続スキルが失敗した場合でも、完了済みの振り返り結果は保持する。

### STEP 8. レポートの最終更新

後続スキルの呼び出し結果が確定したら、KPTレポートの「8. 後続処理」を更新する。

記録する内容：

- 呼び出し対象（improve-skill / git-create-pr）
- 呼び出し理由
- 呼び出し結果
- 後続処理の結果
- 未解決事項

後続処理の結果を確認できなかった場合は「未確認」と記録する。

KPTの内容や過去の分析結果は変更しない。

更新後、ファイルを読み直して保存内容を確認する。

この更新をもってretroの処理を終了する。

## 6. 完了報告

処理完了後、呼び出し元に以下を返す。

- 振り返り対象の業務スキル名
- KPTレポートの絶対パス
- Keepの件数
- Problemの件数
- Tryの件数
- スキル品質の改善要否
- 呼び出した後続スキル
- 後続スキルの実行結果
- 未解決事項

改善が必要な場合：

- improve-skillの呼び出し結果を報告する。

改善が不要な場合：

- git-create-prの呼び出し結果を報告する。
- PR番号とURLが取得できた場合は、その情報も報告する。

後続スキルを呼び出せなかった場合は、その理由を報告する。

KPTレポートのパスは、実際に保存したファイルの絶対パスを報告すること。相対パスや推測したパスを報告してはならない。

### 6.1 User Invocation

ユーザーに以下を報告する。

- 振り返り対象の業務スキル
- KPTレポートの保存先
- Keep / Problem / Tryの概要
- スキル品質の改善要否
- 後続スキルの実行結果
- 未解決事項

### 6.2 Skill Invocation

呼び出し元に以下の結果を返す。

- Status: SUCCESS / FAILED
- Skill Name
- Report Path
- Keep Count
- Problem Count
- Try Count
- Improvement Required: YES / NO / UNKNOWN
- Next Skill: improve-skill / git-create-pr / NONE
- Next Skill Result
- Error (失敗した場合のみ)
- Unresolved Items

呼び出し元は、返された結果をもとに後続処理を判断する。

## 7. 禁止事項

- 実行ログに存在しない事象を作らない。
- 成果が確認できない作業をKeepにしない。
- Problemを隠したり、過小評価したりしない。
- 実行していないテストを実施済みと記載しない。
- 根拠のないTryを追加しない。
- KPT作成のために業務スキルの成果物を変更しない。
- 振り返りの過程で業務スキルを勝手に修正しない。
- Gitリポジトリのルート以外を基準にしてKPTレポートを保存しない。
- 現在の作業ディレクトリを基準にした相対パスで保存しない。
- retroスキル自身の配置ディレクトリにレポートを保存しない。
- 指定された `docs/retro-reports/<skill-name>/` 以外にレポートを保存しない。
- Gitリポジトリのルートを特定できない場合、別の場所に代替出力しない。
- 実際の保存先を確認せずにファイル保存を成功扱いにしない。
- KPTレポートの作成・保存が完了する前に後続スキルを呼び出さない。
- スキル改善が必要な場合にretroからgit-create-prを直接呼び出さない。
- スキル改善が不要な場合にimprove-skillを呼び出さない。
- 後続スキルの呼び出し結果を確認せず、成功と報告しない。
- improve-skillによる改善作業をretro自身の作業として報告しない。
- git-create-prによるPR作成をretro自身の作業として報告しない。
- retro自身で業務スキルの修正、commit、push、PR作成を行わない。
- KPTレポートの内容を後続スキルの都合で改変しない。
